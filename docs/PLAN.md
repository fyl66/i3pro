# i3pro 规划书

> 保留 MoTeC C125 硬件，用开源工具链补上 i2 Pro 缺的那一半。
> 本文是**决策记录 + 里程碑 + 验收标准**，`docs/ACCEPTANCE.md` 是可执行的验收清单。

---

## 1. 一句话定位

把「插线拔线拷 `.ld` → 各自开 i2 Pro → 截图传群」这套流程，换成
**一个 `.bat` 启动、浏览器打开、能按赛道距离重叠两圈、链接直接发群里**的本地工作台。

不做的事（本版明确排除）：

| 排除项 | 原因 |
| --- | --- |
| 实时遥测 / 边缘记录仪 / MQTT / Grafana | 车上现在没有这套硬件，先做等于凭空多半个项目 |
| CAN 原始帧回溯、MF4/BLF、AiM 解析 | 数据源不存在或不在痛点上，留到 v2 |
| 写回 `.ld` 给 i2 Pro | 要完整复刻私有二进制并对齐校验字段，风险高、受益面窄 |
| 云端多人协作、账号体系 | 依赖赛场网络；局域网共享 + 分享链接先覆盖 90% 场景 |
| 通用表达式 / Lua 引擎 | 成本在编辑器与缓存失效，不在求值；v1.5 再做 |

## 2. 事实基础（这些不是假设，是量出来的）

| 事实 | 数值 | 影响 |
| --- | --- | --- |
| 真实数据 | 8 个 C125 `.ld`，36.6–118.8 MB | 解析器必须 mmap，不能整读进内存 |
| 通道规模 | 342–437 通道，100 Hz 主采样率 | 必须搜索 + 分组，不能平铺下拉框 |
| MoTeC `Distance` 通道 | **恒为 0**（beacon 未接线） | 距离轴必须自己积分速度算出来 |
| `.ldx` 圈信息 | 全部 `Total Laps = 1` | 切圈不能读文件，必须自己检测 |
| GPS 可用性 | 部分场次 `GPS Speed/Sats/Heading` 全 0，但经纬度有效 | 切圈要有兜底，不能只信 GPS 速度 |
| 速度源 | `Vx KF`（100 Hz 卡尔曼滤波纵向速度）在全部日志中可用 | 距离积分的首选通道 |
| 运行环境 | Windows + Python 3.13（已有 numpy/pandas/pyarrow）；**没有 Rust** | 不能用 i3rs 自编译；参数栈必须纯 Python |
| 网络 | 沙箱/赛场都可能没有外网 | 运行时零依赖、零 CDN、零 npm |

## 3. 架构

```
i2pro_data/*.ld ──► i3pro.ld (mmap 原生解析) ──┬──► i3pro.store ──► Parquet + meta.json ──► SQL / 列式裁剪
                                              │
                                              ├──► i3pro.derive ──► 速度 / 距离 / GPS 轨迹
                                              ├──► i3pro.laps   ──► GPS 起终点门切圈 + 距离轴重叠 + Δ时间
                                              └──► i3pro.render ──► 自包含 HTML 工作台
                                                                 └──► i3pro.server (stdlib HTTP) ──► 局域网 + 可分享 URL
```

技术选型的理由，逐条对应第 2 节的事实：

* **纯 Python 标准库 + numpy/pandas/pyarrow**，不引入 FastAPI/Flask/DuckDB：队里已有这几个包，
  运行时零安装、零运维，明年换人只要会 Python 就能改。
* **算法层全是纯函数模块**（`derive` / `laps` / `render.downsample`），不绑框架、有单测，
  这是「人毕业了项目不烂尾」的唯一保障。
* **前端是手写 Canvas + 原生 ES 模块**，不引入 React/uPlot：免 npm、免构建、
  单个 HTML 文件可以邮件发给队友，双击就开。
* **服务端用 `http.server`**：只为「多人同时看 + 链接可分享」存在，不需要进程管理。

### 调研：i2 Pro 的圈速是怎么来的（以及我们差在哪）

**i2 Pro 的做法**（来源：`i2pro-help` 的 Basics 章 + 146 页 Manual）：

> "For circuit racing projects **laps are automatically created between the beacon points**."

* 信标（beacon）来自车载信标接收器或 GPS 坐标；**每一对相邻信标之间就是一圈**。
* `Tools → Lap Editor` 里可以做四件事：
  * **Missed Beacons**：漏掉信标时，手工插入对应的信标时间或圈速；
  * **Offsetting the Beacon**：信标位置和往常不同时，输入一个距离偏移，
    让本场圈速能和以前的数据对齐；
  * **Trusted Laps**：把圈标成可信/不可信，默认进出场圈不可信，报表和自动量程会忽略它；
  * **Restore Laps**：撤销所有手工修改，回到记录仪原本的状态；
  * 还有 **Auto Insert**：按"圈长恒定"的假设自动补齐缺失的信标（原文注明这只是近似）。
* 快捷键 **`SHIFT+F7` Place beacon at cursor**。
* 这些修改**存在 `.ldx` 里**，不改 `.ld`。

**我们的做法**：`laps.py` 里没有任何信标概念——它从 GPS 轨迹里**自动挑**一个起终点门
（10 m 网格里"第一次经过且会再次经过"的那个格子），再数航向一致的门穿越。

**八字能不能切？实测 `20260906- mxy 行政楼八字_原厂设定.ld`（1457 s，437 通道，GPS 正常，43×48 m）：**

| 指标 | 结果 |
| --- | --- |
| 检测出的段数 | 22 段，其中 15 段被标为"完整圈" |
| 每段时长 / 里程 | 约 11.5–16 s / 112–123 m |
| 判断 | **一段 ≈ 一个环，不是一个八字周期**——也就是圈数被数成了两倍 |

原因：八字轨迹自相交，同一个门在一个周期里会被经过两次；航向判据只有在门正好落在
交叉点时才帮得上忙（交叉点两侧航向相反），落在任一环上就会一拍两圈。

所以结论是：**八字这类测试不能靠自动挑门，必须能手工指定信标**——这正好是 i2 Pro
Lap Editor 存在的理由。顺带还暴露一个更根本的问题：八字（以及直线加速）本来就没有"圈"，
有意义的单位是"一次运行"，所以编辑器除了"打信标"还应该支持"按起步/停车自动分段"。

**再往下挖一层（用绕质心的转角验证）：** 把每段轨迹绕自身质心的转角算出来，
15 个"完整圈"里大多数是 **+2.00 圈**、少数是 +1.00 圈——也就是说自动挑门连"一段 = 一个环"
都不成立。所以**不能靠"环的绕向"去区分左环/右环**，正确做法是：

> **一个信标 = 一条圈速序列**。八字就在左右两个环上各放一个信标，两条序列各自独立计时，
> 谁也不用猜。这也正是 i2 Pro 的模型（laps are created between beacon crossings，
> 且允许存在多个信标做分段计时）。

> 所以排在报表与直方图之前。

**我们明确要超过 i2 Pro 的地方**（写进目标，不只是口号）：

| 维度 | i2 Pro | i3pro |
| --- | --- | --- |
| 工作表 / 组件数量 | Standard 限 15 工作表 / 5 图 | 无限制 |
| 视图分享 | 本地文件，队友要装软件 | **URL 一贴就能看**，含工作表、通道、圈、光标区间 |
| 安装 | Windows + 授权 | 零安装；队友甚至不需要 Python（快照 HTML） |
| 自动化 | COM API 需要授权 | 标准库 HTTP API，脚本可直接出日报 |
| 多人同时看 | 不行 | 局域网共享同一份数据 |
| 原始 CAN 帧回溯 | 不提供 | 路线图（需要边缘记录仪） |

**v2（需要新硬件或新数据源才做）**

1. 边缘 CAN 记录仪 + DBC 解码 → 与 `.ld` 同 schema 入库
2. 写回 `.ld` 供 i2 Pro 打开
3. 实时遥测看板（Grafana，不自研）

**已明确不做**（第一轮 Q4 确认）：视频组件、Alarms 告警、外部数学插件（VB.net）、
