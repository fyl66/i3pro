# 什么时候才允许上 Rust：四条可判的性能门槛

性能 map（GitHub #49）的最后一问是"要不要用 Rust 重写"。这份 ADR 不回答"该不该"，
它把"**什么时候才允许开始讨论**"写死：四条能判过 / 不过的门槛、一个触发条件、一张代价表。
所有数字都是本机 2026-10-18 实测（规矩 2），判据全部落在两条命令上（下表的"判据"列）。

**结论**：触发条件今天**成立**（四条里三条不过），但证据指向的不是"换语言"——
12 通道 × 8000 桶的冷路径 118.3 ms 里 **83.9 ms（七成）是 `json.dumps`**，而窄接口候选
`render.downsample()`（分桶包络）只有 **19.5 ms（16%）**、整段组装 **25.9 ms（22%）**。
换语言最多动这 19.5 ms；要过 50 ms 这条线，得先动**载荷格式**（二进制帧 / TypedArray 直传），
那是协议改动，不是语言改动。

## 四条门槛（每条都能判过 / 不过）

| # | 门槛 | 判据（哪条命令的哪一列） | 2026-10-18 实测 | 过？ |
| --- | --- | --- | --- | --- |
| 1 | 服务端 `/trace` 计算 **≤ 50 ms**（12 通道 × 8000 桶） | `python tools\bench_viewer.py --http --repeat 3` 的「计算 ms」列，8000 桶那一行（走 `Api.handle`，冷路径） | 高避 **118.3** / 耐久 **170.2** ms | **不过**（2.4× / 3.4×） |
| 2 | HTTP/浏览器端到端 **≤ 150 ms** | 同一条命令的「gzip 冷/热 ms」列（浏览器真走的那条：带 `Accept-Encoding: gzip`） | 高避 **170.9** / 耐久 **229.9** ms（明文那条 137.8 / 186.4 也不都达标） | **不过** |
| 3 | 拖拽缩放每帧 **≤ 16 ms** | `python tools\verify_clicks.py` 的 `#56` NOTE：真鼠标拖 12 步 / 滚轮 6 格，每次事件的墙钟**减掉同一趟量出的空转派发基线** | 拖拽中位 **29.2 / 32.0** ms（两次跑）− 同趟基线 **11.3 / 5.8** ms = **17.9 / 26.2** ms（最大 34.5）；滚轮中位 29.8 / 16.2 ms | **不过**（差 1.1–1.6×，不是 3.7×） |
| 4 | 长帧（**> 50 ms**）**为零** | 同上 NOTE：派发墙钟里 > 50 ms 的个数、浏览器 `PerformanceObserver({entryTypes:['longtask']})` 报的条数，两条都要 0 | 两次跑都是：拖 12 步 **0** 个 · 缩 6 格 **0** 个 · Long Task **0** 个 | **过** |

同一天两次跑里还有几个数，一起记下来免得下次对不上：

- 整屏 `renderAll()`（缓存全失效，**最坏情况**）：两次跑 **59 / 68 ms/帧**（59 那个数就是
  A97 记下来的）。它和门槛 3 的稳态数不是一回事：拖拽时 `renderAll()` 复用抬头与表格
  缓存，最坏情况那一下是全重建。两个数都留着：**门槛看稳态，回归线
  （`verify_clicks.py` 里那条 `< 100 ms`）看最坏情况**。
- "减基线"是两次测量各自的中位数相减，它本身有抖动（同一天两次跑出 17.9 与 26.2 ms）。
  结论不受影响（都 > 16 ms），但**它不是 0.1 ms 级别的判据**——想要更准，得把帧计时
  挪进页面里（今天没做，理由见"量具的口径"第 3 条）。
- `verify_clicks.py` 这一趟 **303 项检查：303 通过、0 失败**（含新加的 3 条）。

### 量具的口径（"长帧"到底怎么算）

门槛 3、4 的判据是 `tools\verify_clicks.py` 里 `#56` 那一段，做法固定下来：

1. 真 Edge、金标准场次、8000 桶档，把窗口缩到**一圈**上（整段全览时一拖就出界，
   数据空了帧会"变快"，量到的是假象）；
2. **真鼠标**按住图表平移 12 步（每步 12 px、间隔约 16 ms），松开；再用真滚轮连缩
   6 格（每格 `deltaY = -120`、间隔约 50 ms）。一次 `mousemove` / `wheel` 就是一次
   `renderAll()`，量的就是那一次事件的主线程墙钟；
3. 同一个脚本先量一条**空转派发基线**（鼠标在图外移动一次，不触发重画）——那是 CDP
   协议自身的往返，用户不付这个钱，所以门槛 3 读的是"墙钟 − 基线"；
4. 长帧另用浏览器自己的 `Long Task API` 交叉印证：它报的主线程任务条数，与上面按
   50 ms 数出来的应当一致。

**这条只覆盖一种拖法**（一圈窗口、8000 桶、单张图、每步 16 ms）。"拖到触发重取数"、
多组件工作表、更碎的鼠标输入都没覆盖——门槛 4 的"零"是**这种拖法下**的零。

## 触发条件

照 #56 票面：**本 map 其余票全部关闭，且四条里仍有一条不达标**，才允许另开一张 ADR
讨论"窄接口"（票面写"其余五张"，加上后来拆出的 #63 一共六张）。今天：其余六张
（#51 / #52 / #53 / #54 / #55 / #63）全关，门槛 1 / 2 / 3 不过 → **触发条件成立**。

成立的意思是"允许开那张 ADR"，不是"应该上 Rust"。真开的话，那张 ADR 至少要回答：

1. 拿 profiler 的拆分数字说清**是哪一段**在超（不是只报一个总耗时）；
2. 那段为什么在 Python / numpy 里压不下去——今天的两条反证：`json.dumps` 本来就是 C 写的，
   分桶已经是 `np.add.reduceat`（#53，逐位一致）；
3. 窄接口的退出方式（见"代价"最后两条）；
4. Python 版本 × 平台的分发账，以及"双击 `启动.bat` 就能用"还成不成立。

## 窄接口候选（只列，不实现）

票面点了两个名字，落到今天的代码是这样：

| 候选 | 今天在哪 | 实测代价 |
| --- | --- | --- |
| `downsample_envelope` | `src/i3pro/render.py` 的 `downsample()`（由 `trace()` 调用） | 今天实测：12 通道 × 8000 桶分桶 **19.5 ms**（#53 那趟是 18 ms——`np.add.reduceat` 之后就是这个量级）；整段组装中位 **25.9 ms** |
| `scale_channels` | 今天**没有**同名函数：纵轴量程在前端 `groupScaleFor()` 里算（浏览器里），值域处理散在 `render.trace` 与 `derive` | 前端那段换语言也换不掉（画布是浏览器画的）；Python 那段已经算在上面那 25.9 ms 里 |

同一趟探针（同一份数据、同一档、同一台机器，把 `json.dumps` 与组装分开量）：

| 冷路径 118.3 ms 的去向 | 中位 |
| --- | --- |
| 组装（`render.trace` × 12 + 时间轴 + 距离积分） | **25.9 ms** |
| 　└ 其中：取数前的重采样 `derive.upsample_to_master` × 12 | 6.6 ms |
| 　└ 其中：分桶包络 `render.downsample` × 12（**= 窄接口候选**） | 19.5 ms |
| `json.dumps(payload)` | **83.9 ms** |
| 其余（请求拆解、UTF-8 编码、`_send`） | 约 8 ms（118.3 − 25.9 − 83.9，减法推出来的） |

探针与 `bench_viewer.py` 的计算列差一次 `handle` 往返，**别把 25.9 + 83.9 当成 bench 那两行去对读**；
要看趋势就看 bench 的整列，要看拆分就看这条探针。

## 代价（真上的话）

- **本机没有 Rust**（[`docs/PLAN.md`](../PLAN.md) 的"事实基础"表里就写着这一条）：这台机器与
  队友机器都得先装工具链，否则只能收**预编译的 `.pyd`**。
- **按 Python 版本 × 平台分发**：今天只有 Windows + CPython 3.13 一条线；队友换 3.12 / 3.14
  或 arm64，就得再来一份二进制——"一个 `.bat` + 一份数据"的离线承诺会变成"N 份二进制"。
- **与"双击 `启动.bat` 就能用"的关系**：`启动.bat` 现在只要求 Python 与那几个包。加扩展之后
  必须**先算清**三选一——随包发 `.pyd`（Python 版本一换就废）、首次启动联网装工具链（破离线）、
  构建在仓库外产出（多养一条构建链）。ADR-0006 放宽的是"允许 vendored 单文件依赖"，
  **没有**放宽"双击就能用"。
- **修一次算法要过两边的测试**：Python 侧五件套照旧，外加 Rust 侧的构建与"逐位相同"单测。
- **退出方式（照 #53 的先例）**：窄接口保持纯函数（numpy 数组进、数组出），Python 侧留等价
  实现与逐位相同的单测；删掉 Rust 只是回落到慢实现，行为不变。
- 规则 4 说新增运行期依赖要先写 ADR：`downsample_envelope` 这类扩展就是一条新的运行期依赖，
  这份 ADR 是那道闸——**门槛不达 + 上面四条答完之前不批**。

## 翻案条件

出现下面任意一条，这份 ADR 就该重写：

1. 冷路径的 `json.dumps` 被换成二进制载荷（或别的格式），门槛 1 重新量过——那时组装那
   25.9 ms 才变成大头，窄接口才有意义；
2. 帧那 59–68 ms（最坏情况）或 17.9–26.2 ms（拖拽稳态）被拆开量过，证明瓶颈在 Python 侧
   而不是浏览器（今天还没拆过，见 map 的 "Not yet specified"）；
3. 四条门槛全部达标——那就没有理由再开 Rust 那张 ADR。

## Considered Options

- **现在就上 Rust / PyO3 重写分桶与缩放**：否决。瓶颈（83.9 ms 的序列化）不在候选接口里，
  代价（多平台分发 + 破坏"双击就能用"）却要照单全收。
- **不设门槛，凭感觉决定**：否决。下一个维护者拿不到"现在到底算快还是慢"的判据，
  性能 map 这一轮也就白走了。
- **本 ADR 的路线**：四条可判的门槛 + 一个触发条件 + 一张代价表。够不够得着由数字说话，
  不由偏好说话。
