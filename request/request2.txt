### 现成的替代与升级方案

赛车运动与高频时序数据分析领域，MoTeC i2 Pro 拥有很高的圈速重叠比对能力，Marple 则长于现代化 Web 化与自动化协作。业内常用的替代工具覆盖不同应用场景：

| 工具名称 | 类型 | 适用场景与定位 | 特点与优势 |
| --- | --- | --- | --- |
| **Plotly Dash / Streamlit** | 开源生态 | 自建 Web 分析看板 | 基于 Python，结合 `Plotly` 快速搭建交互式图表，适合定制特定计算逻辑。 |
| **Grafana + InfluxDB/TimescaleDB** | 开源平台 | 实时遥测与赛道边缘监控 | 适合做实时流监控、传感器健康检查看板；但在多圈重叠（Lap Overlay）和距离轴对齐上偏弱。 |
| **Friss/i3rs** | 开源软件 (Rust) | MoTeC i2 Pro 本地开源平替 | 针对 MoTeC `.ld/.ldx` 文件解析，跨平台（支持 Mac/Linux），支持多圈对比、降采样与多轴同步。 |
| **Bosch WinDarab** | 商业/免费版 (顶级升级) | 顶级赛事深度数据分析 | F1/WEC 级别专业工具，虚拟通道、多物理量建模与数学公式比 i2 更灵活，但上手门槛高。 |
| **McLaren ATLAS** | 顶级商业软件 | 实时/后处理顶级标杆 | F1/Formula E 标杆，支持大规模分布式采集与深度遥测，成本极高。 |
| **AiM RaceStudio 3** | 专有免费 | 普及型赛车/卡丁车数据分析 | 具备完善的 GPS 轨迹重构、多圈切片比对与视频同步功能，格式相对封闭。 |

### 开源自研方案：实现难度与技术选型

如果团队想自建一套类似 Marple 的“现代 Web 遥测/数据分析平台”，**实现技术完全可行**，但需要避开传统 Web 报表的性能坑（例如几百万个采样点直接推给浏览器会直接卡死崩溃）。

#### 推荐技术架构

* **数据接入与解析（Ingestion & Parsing）：**
* **底层协议：** 赛车下发通常是 CAN 总线日志（`.blf`, `.asc`, `.mf4`）或由车载模块转出的 CSV/Parquet。
* **开源库：** Python 生态中的 `asammdf`（用于 MDF4 格式，汽车行业工业标准）、`cantools`（加载 DBC 文件解析原始 CAN 帧）。


* **高性能存储引擎（Storage）：**
* **离线文件：** 强烈推荐 **Apache Parquet / Arrow**。列式存储读单个传感器（如仅读取 `Engine_RPM`）速度比 CSV 快数十倍，原生支持压缩。
* **在线/时序库：** **ClickHouse** 或 **TimescaleDB**。如果数据量在百万到亿级，ClickHouse 的时序查询吞吐量极佳。


* **前端可视化与交互（Frontend Rendering）：**
* **核心图表库：** 绝不能用默认的 ECharts 或 SVG 图表，必须选 **WebGL / Canvas 加速** 库：
* **uPlot**：极其轻量、渲染速度极快，可在 Canvas 上流畅缩放平移几十万数据点。
* **SciChart (Web版)** 或 **Plotly.js (WebGL 模式)**：适合多 Y 轴、光标对齐以及多面板联动。




* **核心计算引擎：**
* 用 Python 或 Rust 写后台 API，实现**分圈逻辑（Lap Trigger/GPS 坐标切分）**和**距离归一化（将时间轴转换成赛道绝对距离轴）**。



#### 自研核心难点

1. **X 轴对齐（Time-based vs. Distance-based）：**
* MoTeC 最强的核心是按赛道距离（Distance）重叠两圈，而非时间。自研时必须先根据车速对时间做积分（或基于 GPS 经纬度做赛道投影计算里程），重新做线性插值以统一采样步长。


2. **大数据量降采样渲染（Min-Max Decimation）：**
* 当分析一个 1 小时的测试、采集频率 1000 Hz（360 万点）时，前端无法完整渲染。需要服务端或 Web Worker 实现 **LTTB (Largest Triangle Three Buckets)** 或 **Min-Max 降采样算法**，根据当前视口像素宽度动态提取极值点。


3. **虚拟/数学通道（Math Channels）：**
* 工程师通常需要写公式（如滑移率、瞬时功率、悬架速度微分）。系统需要一个表达式计算器（例如 Python 的 `numexpr` 或嵌入式 JavaScript/Lua 引擎）。



---

### 推荐落地路线

* **如果不想重复造轮子：** 尝试评估 **i3rs**（Rust 开源本地客户端），或者直接写 Python 脚本借助 `asammdf` / `cantools` 统一把外部数据转换成 MoTeC 的 `.ld` 格式（社区有成熟的 `MotecLogGenerator` 等开源转换器），继续利用 i2 Pro 成熟的分析模板。
* **如果坚持做现代化 Web 平台：** 推荐以 **Next.js + uPlot + FastAPI + Parquet/DuckDB** 为基础骨架。先打通“DBC 转换 -> Parquet 存储 -> WebGL 双光标联动”，即可在 2~3 周内完成高可用原型。



在大学生电动方程式（FSE）赛车开发与测试中，**MoTeC C125 + i2 Pro** 的确是底盘动力学分析的行业标杆，但面临明显的痛点：

1. **协作与流转低效**：每次试车结束都要插线拔线拷 `.ld` 文件，数据散落在不同队员的笔记本上，无法多人协同分析。
2. **BMS/电驱海量通道吃力**：三电系统动辄 140+ 节单体电芯电压、数十个温度测点、逆变器相电流与调制比，C125 记录内存（通常 120MB）和通道数上限极易见顶。
3. **缺少实时遥测（Live Telemetry）与自动化**：P房无法实时监控绝缘电阻、单体过温等安全预警；测试后无法一键出具制动测试、能耗与电机热衰分析报告。

一套集成了 **MoTeC 的赛车级赛道距离重叠分析能力** 与 **Marple 的现代 Web 协作/海量通道即时查看能力** 的综合方案，可以按照以下分层架构进行规划落地：

```
[ 整车 CAN 3 (底盘/IMU/轮速) ] /          |
                                         +--> [ 离线高速落盘: SD卡 / NVMe (Parquet/MF4) ]
                                         +--> [ 4G/5G/Wi-Fi 遥测推流 (MQTT / Protobuf) ]
                                                        |
                                          ==============================
                                            P房基地台 / 云端分析服务
                                          ==============================
                                                        |
     +--------------------------------------------------+--------------------------------------------------+
     |                                                                                                     |
[ 实时流 (Live Telemetry) ]                                                                    [ 离线/赛后深度分析 (Web + Desktop) ]
  - Mosquitto -> InfluxDB / ClickHouse                                                           - DBC 自动解析 -> DuckDB / Parquet 列式存储
  - P房大屏: Grafana 看板 (BMS温度、母线功率、故障码)                                               - Web 端: 自建 uPlot/Marple (波形缩放/多人共享)

```

### 模块方案与技术选型

#### 1. 数据采集与传输（Hardware & Edge）

不建议完全抛弃 C125（其仪表显示与驾驶员交互非常稳定），但应**卸载其高频全量记录压力**：

* **硬件加装：** 增设专用的边缘数据记录仪，例如 **CSS Electronics CANedge2/3**（自带 Wi-Fi/4G 自动回传），或自研 **Raspberry Pi CM4 / 嵌入式 Linux (如 STM32MP1/全志 T113)** + CAN FD 扩展板。
* **双模式采集：**
* **全量原始帧落盘：** 实时将 3 路 CAN 总线原始帧以二进制（如 MDF4 或自定义压缩结构）写入高速 SD 卡，彻底解放通道数量和采样率限制。
* **抽样遥测推流：** 车载端将核心安全参数（TSAL 状态、最高/低电芯电压、最高温度、母线电流、逆变器状态）以 10–50 Hz 通过 MQTT 协议经过 4G/Wi-Fi 发送至 P 房。



#### 2. 数据解析与底层存储（Data Pipeline）

采用现代化数据栈替代老旧的私有二进制格式：

* **DBC 自动化解析：** 后端服务接入 `cantools` 或 `asammdf`（Python 生态成熟利器），上传最新车队 DBC 后，自动把原始 CAN 报文解码为具名工程物理量。
* **列式存储（Core）：** 采用 **Apache Parquet** 或内嵌分析数据库 **DuckDB**。相比 CSV，Parquet 压缩比高达 80% 以上，读取 100+ 单体电压特定时间段只需数毫秒，与 Marple 的底层存储机制一致。

#### 3. 核心算法引擎：解决 MoTeC 的核心护城河

很多 Web 图表替代不了 MoTeC 的根本原因在于缺少**赛车动力学分析逻辑**。需要在自研服务端或客户端集成以下算法：

* **赛道距离归一化（Lap Distance Interpolation）：**
* GPS 采样通常只有 10–20 Hz，轮速计有 100 Hz。通过对轮速积分或 GPS 轨迹投影计算赛道绝对累计里程 $s$。
* 根据预设的起点/终点坐标（Lap Trigger）对数据切圈。
* 将时间轴映射为**赛道距离轴**，并执行均匀插值重采样，实现多圈速度、转向角、油门刹车曲线的**高精度重叠比对（Lap Overlay）**。


* **虚拟数学通道（Math Channels）：**
* 动态计算滑移率（Slip Ratio）、瞬时机械输出功率、各轮扭矩分配差值、前后制动力分配比（Brake Bias）。


* **动力学图表支持：**
* **G-G 图（Kamm's Circle）：** 横向加速度与纵向加速度散点图，直观评估车手极限利用率。
* **弯道分析器（Corner-by-Corner）：** 自动根据赛道曲率切分弯道（刹车点、APEX、出弯加速点），生成扇区对比报表。



#### 4. 前端交互与协作层（UI & UX）

结合现代 Web 技术的优势，打造团队共享平台：

* **高性能波形组件：** 前端千万不要用常规的 ECharts（大量点直接卡死）。推荐使用 **uPlot**（极低内存、Canvas 渲染数十万点依然 60fps）或商业授权对学生团队友好的 **SciChart Web**。
* **双光标（Cursor Sync）与多图联动：** 拖动时序图光标时，赛道轨迹图上的车辆位置同步移动。
* **多用户实时共享：** 基于 URL Hash（例如 `?run=20260912_run1&laps=2,3&ch=Speed,APPS,Brake_Press`）让不同分系统负责人（底盘、三电、电控）直接在浏览器中打开同一个视图讨论，告别“截图传群”。

### 两全其美：双轨兼容策略

完全抛弃团队使用多年的 MoTeC i2 Pro 工作流通常是不现实的，最稳妥的策略是“向前兼容，向后升级”：

| 方案 | 负责阶段 | 工具选型 | 交付与体验 |
| --- | --- | --- | --- |
| **实时/P房级** | 赛道测试中 | 4G/Wi-Fi + MQTT + InfluxDB + Grafana | 实时安全红线报警（电芯压差、绝缘阻抗、逆变器过热）。 |
| **现代协同级** | 试车间隙/赛后复盘 | Web 平台（自建 / Marple 教育版） | 几秒内完成整车 500+ 通道检索、电芯极值筛选、能效报表自动生成。 |
| **赛道极限调校** | 深度动力学/底盘 | MoTeC i2 Pro（保持兼容） | 自研后端通过 Python 开源库（如 `ldparser` / `MotecLogGenerator`）将解析后的数据直接**一键导出为 `.ld` 文件**，动力学工程师继续使用积淀多年的 i2 Workspaces。 |

---

### 关键落地路径（分三步推进）

1. **第一阶段（数据底座打通，约 1~2 周）：**
* 使用 Python 搭建离线转换脚本：`CAN 日志 (.mf4/.blf) + DBC 文件 -> Parquet 文件`，同时提供转出 `MoTeC .ld` 的接口。这一步即使不做前端，也能大幅提升团队数据提取效率。


2. **第二阶段（轻量 Web 查看器，约 2~3 周）：**
* 基于 FastAPI + DuckDB 构建后端，前端采用 Next.js + `uPlot`。
* 实现核心交互：通道搜索勾选、时间轴缩放、切圈与两圈重叠对比。


3. **第三阶段（赛道特定分析与实时集成，后续迭代）：**
* 增加赛道地图轨迹联动（GPS 渲染）、G-G 散点图以及距离轴对齐算法。
* 接入 P 房 4G 遥测推流，实现实时/历史一体化。
