这两份文档方向是一致的（保留 C125 数据源 + 开源现代化平台 + 与 i2 Pro 双轨兼容），我在此基础上做一份更细的落地规划。核心优化思路有三点：**把"双轨数据流"讲清楚（这是两份文档交叉但没钉死的部分）、给每个阶段加上可验收的交付物和工时、把技术难点前置评估风险**。

## 一、产品定位与需求分层（先钉死"做什么"）

### 用户角色与核心诉求

| 角色 | 高频操作 | 对平台的要求 | 现状痛点 |
|---|---|---|---|
| 底盘/车手工程师 | 多圈重叠、G-G 图、刹车点对比 | 距离轴对齐精度、双光标联动 | i2 Pro 够用但数据流转慢 |
| 三电工程师 | 140+ 电芯电压/温度筛选、极值定位、绝缘/温差报警 | 海量通道秒级检索、阈值筛选 | C125 通道数/内存上限 |
| 电控工程师 | 故障码追溯、CAN 原始帧回放 | 原始帧级回溯能力 | `.ld` 里只有解码后通道 |
| 车队经理/全体 | 试车日报、能耗/圈速报表 | 一键生成、URL 分享 | 靠截图传群 |

### 需求优先级（建议 P0/P1/P2 划分）

- **P0（没有它方案就没价值）**：`.ld` 解析导入、Parquet 存储、时间轴波形查看、双圈重叠（距离轴）、通道搜索
- **P1（形成对 i2 Pro 的优势）**：URL 视图共享、虚拟数学通道、G-G 图、电芯极值/压差自动筛选报表
- **P2（差异化能力）**：实时遥测推流、弯道自动切分、视频同步、自动导出 `.ld` 回灌 i2 Pro

关键判断：**P0 里必须包含"距离轴多圈重叠"，因为这是你们不抛弃 i2 Pro 的唯一理由，自研平台做不到这一点就没人用。**

## 二、技术路线优化：钉死双轨数据流

两份文档各提了一条数据路径，需要合并成一张明确的图：

```
轨 A（现有资产，低频全量）
  C125 → .ld/.ldx 文件 → [i3rs 验证 / ldparser 解析] → Parquet
        ↘ 一键导出 .ld 回灌（兼容老工作流，P2）

轨 B（新增能力，高频海量）
  3× CAN 总线 → Edge Logger（CANedge2/3 或 CM4 自研）
        → 原始帧落盘 SD（MF4/BLF，全量、1000Hz 无压力）
        → 4G/Wi-Fi 抽 10-50Hz 安全参数 → MQTT → P房实时看板
        ↓ 赛后
  asammdf/cantools + DBC 解码 → Parquet（与轨 A 同库同 schema）

统一存储层：Parquet + DuckDB（单机期）→ 可平滑迁 ClickHouse（协作期）
统一服务层：FastAPI
统一前端：Next.js + uPlot
```

**关键决策点（建议现在定下来）：**

1. **两条轨的 Parquet schema 必须统一**——同一场比赛的数据无论来自 C125 还是 Edge Logger，落库后表结构一致，否则多圈对比会跨数据源断裂。建议 schema：`timestamp | lap | distance | <channel_1>...<channel_n>`，宽表 + 每场比赛一个文件/分区。
2. **DBC 版本管理进 Git**——`cantools` 解码依赖 DBC，DBC 迭代频繁，必须和代码同仓管理，且每次转换记录 DBC 的 commit hash，否则历史数据会"解码漂移"。
3. **时钟同步问题前置**——C125、Edge Logger、GPS 各自时钟不同源，合并分析前必须以 GPS PPS 或赛后对齐脚本统一时间基准。这是最容易被忽略、后期最难补的坑。
4. **Edge Logger 选型**：第一期直接买 **CANedge2**（约 2-3k 元级，自带 Wi-Fi 自动回传），不要自研硬件——自研 CM4 方案在车队环境（振动、EMC、供电瞬断）下的可靠性成本远超采购价。自研只作为二期有明确余力时的项目。

## 三、技术栈明细（可直接开工的级别）

### 后端 / 数据管道

| 层 | 选型 | 版本/说明 |
|---|---|---|
| `.ld` 解析 | `ldparser`（Python）+ i3rs（人工验证工具） | i3rs 只用来交叉验证解析正确性，不作为依赖 |
| CAN 解码 | `asammdf`（MF4/BLF）+ `cantools`（DBC） | 汽车行业标准库，稳定 |
| 存储格式 | Parquet + `pyarrow` | zstd 压缩，按 `event/date` 分区目录 |
| 查询引擎 | DuckDB | 直接 `read_parquet()`，零运维；预留迁移 ClickHouse 的 SQL 兼容层 |
| 计算 | `pandas` + `numexpr`（虚拟通道） | 虚拟通道表达式编译为 numexpr，比 eval 安全且快 |
| API | FastAPI + Pydantic | 异步，文件上传/任务队列用 BackgroundTasks，够用到协作期 |
| 降采样 | 服务端 LTTB + Min-Max 混合 | 见下文算法细节 |
| 任务队列（二期） | 不用 Celery，用 `arq` 或 SQLite 队列表 | 避免过早引入 Redis |

### 前端

| 项 | 选型 | 理由 |
|---|---|---|
| 框架 | Next.js (React) + TypeScript | 生态、SSR 对首屏大数据列表友好 |
| 图表 | **uPlot** 为主，赛道轨迹用 MapLibre GL / 自绘 Canvas | 坚决不用 ECharts 渲染波形 |
| 状态/共享 | URL 即状态（run/laps/channels/cursor 全编码进 query） | 这是"截图传群"的根治方案，成本极低收益极大 |
| 多人协作 | 一期用 URL 分享；二期加 WebSocket 光标广播（可选） | 不要一期就上 CRDT，过度设计 |

### 算法细节（三个难点的具体做法）

1. **距离轴对齐**：轮速 100Hz 积分为主（`distance += v·dt`，用左右轮速均值减少打滑误差），GPS 10-20Hz 做**漂移校正锚点**（每过 GPS 点把积分里程向 GPS 投影里程收敛，比例系数 0.1-0.3 逐步校正，避免 GPS 跳变直接污染积分）。切圈用起点线 GPS 坐标 + 航向判定。最后两圈按 1m 步长线性插值重叠。
2. **降采样**：视口 ≤2000px 时，每像素列保留 min+max 两点（保极值，波形不失真），缩放后细节区切换 LTTB 保形状。**不要全量用 LTTB**——Min-Max 保极值对电芯电压尖峰检测至关重要。缓存按 `(文件, 通道, 像素宽度)` 分级预计算。
3. **虚拟通道**：表达式如 `slip = (w_f_avg - v_gps) / max(v_gps, 1)`，用 numexpr 向量化计算，计算结果按需落 Parquet 缓存列，避免每次重算 360 万点。

## 四、分阶段路线（带验收标准与工时）

### 阶段 0：验证期（约 1 周，1 人）

- 用 Python 写 `.ld → Parquet` 转换脚本（基于 ldparser），跑通 1 场真实试车数据
- **验收**：转换 1 个 100MB `.ld` < 30s；随机抽 3 个通道与 i2 Pro 显示值误差 < 0.5%
- 同时装 i3rs 给底盘工程师试用，收集"比 i2 差在哪"的清单——这决定 P0 的功能排序

### 阶段 1：数据底座 + CLI 工具（1-2 周，1-2 人）

- CAN 日志（MF4/BLF）+ DBC → Parquet 管线，与 `.ld → Parquet` 输出同 schema
- DuckDB 封装成 CLI：`query "SELECT max(cell_v_57) FROM run_0912 WHERE lap=3"`
- **验收**：一场 40 分钟三路 CAN 数据（约 3-5GB 原始）转换 + 入库 < 10 分钟；任意单通道任意时间段查询 < 1s

### 阶段 2：Web MVP（2-3 周，2 人）

- FastAPI + DuckDB + Next.js + uPlot
- 功能严格限定 P0：上传/选场次 → 通道搜索勾选 → 时间轴缩放（Min-Max 降采样）→ 选两圈 → **距离轴重叠对比** → URL 分享视图
- **验收**：单次会话 20 通道 × 100 万点，缩放平移保持 60fps；非技术人员不看文档能完成一次双圈对比
- ⚠️ 这是全项目风险最高的阶段，uPlot 的多轴/同步光标要预留 1 周 buffer

### 阶段 3：分析深度（2-3 周，可与阶段 2 后半并行）

- 虚拟数学通道（表达式编辑器）
- G-G 图、电芯压差/极值自动筛选报表（三电工程师的第一个"wow 时刻"）
- Lap 自动切分 + 圈速表

### 阶段 4：实时遥测 + 回灌（按需）

- CANedge MQTT → Mosquitto → InfluxDB → Grafana P 房看板（注意：**实时看板直接用 Grafana，不自研**）
- 回灌链路：平台数据 → 生成 `.ld`（MotecLogGenerator）→ i2 Pro 打开，彻底打通双轨

## 五、主要风险与对策

| 风险 | 概率/影响 | 对策 |
|---|---|---|
| 距离轴对齐精度不够，底盘组不认 | 中/高 | 阶段 0 就用 i2 Pro 的重叠图做基准对比，误差 >2% 不进入阶段 2 |
| 学生团队人员流动，平台烂尾 | 高/高 | 阶段 1 的 CLI 工具本身就是保底交付物；代码强制类型注解 + 文档即 README；核心逻辑（对齐/降采样）写成纯函数模块，不绑框架 |
| GPS 信号差（雨战/遮挡）导致切圈失败 | 中/中 | 切圈支持手动打点 + 基于车速模式的兜底切分 |
| DuckDB 并发写入冲突 | 低/中 | 转换任务串行化（写入临时文件 + 原子 rename），读取天然并发安全 |
| 4G 赛场信号差，实时链路断 | 高/低 | 车载端本地缓存断点续传；实时看板定位为"安全预警辅助"而非唯一监控手段，C125 仪表保持兜底 |
